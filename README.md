# Laser Booking Kiosk

A wall display for a Raspberry Pi that shows whether the laser cutter is free,
based on a public Google Calendar.

- **Green banner:** `LASER IS FREE`
- **Orange banner:** `LASER IS BOOKED UNTIL HH:MM`
- **Grey footer:** `Next booking is on Sat 24 Oct 01:00 to 01:59`
- **Middle:** a list of upcoming bookings, with the current one highlighted

Back-to-back bookings are chained, so 14:00–15:00 followed by 15:00–16:00 shows
"booked until 16:00".

## How it works

```
Google Calendar (public iCal feed)
        │  every minute (cron)
        ▼
update_calendar.py ──► status.json ◄── index.html (polls every 30 s)
                                            │
                              Chromium in kiosk mode on the Pi
```

1. **`update_calendar.py`** downloads the calendar's public `.ics` feed, expands
   recurring events, works out the current and next booking, and writes
   `status.json`. It retries on network errors and writes an error into the
   file if the calendar can't be reached.
2. **`index.html`** is a static page that reads `status.json` every 30 seconds
   and draws the banners and booking list. If the data is older than
   5 minutes or contains an error, it shows `STATUS UNAVAILABLE` instead of a
   possibly wrong "FREE".
3. **A local web server** (`python3 -m http.server`, bound to 127.0.0.1) serves
   the folder, because browsers block `fetch()` from `file://` pages.
4. **`kiosk.sh`** (generated by `deploy.sh`) waits for the network, refreshes the
   data once, then starts Chromium fullscreen.

No Google Cloud account, API key or OAuth is needed.

## Requirements

- Raspberry Pi running Raspberry Pi OS **Trixie** (Debian 13) with the labwc desktop
- Desktop autologin enabled (`sudo raspi-config` → System Options → Boot / Auto Login)
- Timezone set correctly (`sudo raspi-config` → Localisation), since the displayed times use it
- A Google Calendar shared publicly with **See all event details**

## Setup

1. In Google Calendar, open the laser calendar's **Settings and sharing**:
   - Under *Access permissions for events*, tick **Make available to public**.
   - Under *Integrate calendar*, copy the **Public address in iCal format**.
2. Put that URL in `URL` at the top of `update_calendar.py`. Check it works:
   ```bash
   curl -sI "YOUR_URL" | head -1     # expect HTTP/2 200
   ```
3. Clone the repo on the Pi and deploy:
   ```bash
   git clone git@github.com:YOUR_USER/laser-kiosk.git ~/laser_kiosk
   cd ~/laser_kiosk
   ./deploy.sh
   sudo reboot
   ```

`deploy.sh` is idempotent, so to update later run `git pull && ./deploy.sh`.
Use `./deploy.sh --no-kiosk` to skip Chromium, autostart and cursor setup
(for example on a development machine).

### What `deploy.sh` does

- Installs `python3-venv`, `cron`, `curl` and `chromium` with apt
- Creates `.venv` and installs `icalendar` and `recurring-ical-events`
- Adds two tagged crontab entries: the updater (every minute) and the local web server (at boot)
- Generates `kiosk.sh` and registers it in `~/.config/labwc/autostart`
- Installs a transparent cursor theme and disables screen blanking

## Configuration

| Setting | Where | Default |
|---------|-------|---------|
| Calendar URL | `URL` in `update_calendar.py` | |
| Look-ahead window | `DAYS_AHEAD` in `update_calendar.py` | 30 days |
| Bookings shown on screen | `MAX_EVENTS_ON_SCREEN` in `index.html` | 8 |
| Stale-data cutoff | `5 * 60 * 1000` in `index.html` | 5 minutes |
| Port | `PORT` in `deploy.sh` | 8000 |

The display can't scroll, so if the last card is cut off on your screen, lower
`MAX_EVENTS_ON_SCREEN`.

## Operating the kiosk

- **Exit kiosk mode:** `Alt+F4` on a keyboard, or `pkill chromium` over SSH.
  Tapping the screen won't help.
- **Stop it launching at boot:** comment out the `# laser-kiosk` line in
  `~/.config/labwc/autostart`.
- **Logs:** `journalctl -t laser-kiosk -n 20`
- **Check the data:** `cat status.json`
- **Run the updater by hand:** `.venv/bin/python update_calendar.py`

## Troubleshooting

| Symptom | Likely cause |
|---------|--------------|
| `STATUS UNAVAILABLE` with "stale" | Cron isn't running; check `crontab -l` and the logs |
| `STATUS UNAVAILABLE` with "Failed to fetch" | The page was opened as `file://` or the web server isn't running |
| Stuck on `LOADING…` | JavaScript syntax error; press F12 and check the console |
| HTTP 404 from the updater | Wrong iCal URL, or the calendar isn't shared publicly with event details |
| "Temporary failure in name resolution" at boot | Network not up yet; usually clears itself (the updater retries) |
| Mouse cursor visible until first moved | labwc draws its default cursor until a client sets one; a boot-time quirk |

## Known limitations

- **All-day events are ignored**, since they don't represent a time slot.
- **Booking titles are displayed.** The calendar is public already, but avoid
  putting private details in titles.
- **Multi-day bookings** are listed under their start day only.
- The cursor may be visible at boot until the pointer first moves.

`compute_status()` is a pure function (no clock or network access), which is
what makes the booking logic testable. Tests cover back-to-back and overlapping
bookings, boundary times, midnight spans, recurring events and all-day events.

GitHub Actions (`.github/workflows/checks.yml`) runs on every push: Python
syntax check, pytest, `bash -n` and ShellCheck on `deploy.sh`, and a Node syntax
check of the script in `index.html`. The CI check extracts the script using the
`<script>` and `</script>` lines, so keep each tag on its own line.
